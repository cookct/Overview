Lagoon v1.3 · Feature Overview

// Lagoon

A local-first AI writing and roleplay workspace. Bring your own API keys — no subscriptions, no cloud accounts, no data leaving your machine.

Lagoon is a character-driven AI chat environment built for long-form collaborative fiction. You define a character — personality, voice, backstory — and have an ongoing conversation powered by your choice of model. The system actively works to keep the story coherent over hundreds of turns: tracking what the character knows, surfacing relevant past context automatically, and correcting the prose habits AI models tend to fall into.

Providers:   Venice.ai  ·  Together.ai  ·  HuggingFace  ·  Local (Ollama)  ·  Any OpenAI-compatible endpoint

BYOK — paste your API keys in settings. No accounts, no middleman. Point Lagoon at any local inference server (KoboldCpp, llama.cpp, LM Studio, Jan, etc.) via Custom Endpoints.

Stack: Python / Flask backend · Vanilla JS frontend · Local JSON storage · python setup.py → python app.py and you're running.

01 Architecture & feature map

Stack: Flask (Python) backend on port 5007 · Vanilla JS frontend · Local JSON file storage · No database, no cloud sync, no accounts.

State: state.js — direct mutable object, single source of truth. All active features read/write it.

Persistence: Chats → chats/{chat_id}.json · Character configs → configs/{name}.json · Summary stacks → chats/.summaries/{chat_id}.summary.json · RAG embeddings → chats/.rag/{chat_id}.rag.json · Lore/Anchors → configs/.lore/{name}.lore.json · Memory settings → memory_settings.json · UI preferences → localStorage.

Chat
SSE-streamed responses from any configured model. Per-character configs, message editing, forking, regeneration, nudge injection, message keeping for export.
Dual Model Mode
Two AI characters conducting an automated conversation with each other. Configurable turn limit, pause/resume, per-character temperature and model override.
Context Management
Token counting via tiktoken. Auto-summarisation at configurable threshold (default 75%) with user approval workflow. Rolling summary stack with continuation-aware prompts. All parameters tunable via Memory Settings.
Author's Note
Re-injection of tone/voice/scene facts at a configurable depth from the bottom of context on every turn. Persistent (config file) or session-only override.
Anchors
Keyword-triggered lore entries with priority and token budget. Built-in character awareness tracking with automated reveal detection and toast notification.
RAG Memory
Semantic retrieval of past conversation chunks using all-MiniLM-L6-v2 (384-dim). Top-k matches by cosine similarity injected silently before each turn. Can be disabled; all parameters configurable via Memory Settings.
Style Overseer
Post-stream LLM agent reviewing each response against a fully configurable rule set. Six built-in rules run by default (toggleable); add your own in plain English or load a model-specific preset. Accept replaces the offending text in-place. Corrected passages are marked with an amber dotted underline. Auto-accept mode runs silently after every response.

02 Chat & character system

Each conversation is tied to a character config — a JSON file in configs/ that defines everything about how that model should behave. Configs are reusable across chats.

Complete character config fields

Streaming flow

User sends message → POST /api/chat with SSE response. The backend emits three event types: start (returns the chat ID, fires once), chunk (a text fragment, fires continuously), end (stream finished). On first chunk the loading spinner is replaced with the rendered message. Markdown is rendered incrementally as chunks arrive.

After the stream ends: chat is auto-saved to disk, RAG indexing runs in the background, Style Overseer fires if enabled.

Markdown rendering

Uses markdown-it with linkify enabled. Before rendering, the pipeline strips: OOC nudge text (( … )), citation markers (word.13, [1], [^1], superscript numbers). <think>…</think> blocks are converted to a collapsible <details> element with a "Thinking…" summary. Fallback: HTML-escaped plain text if markdown-it is unavailable.

Prompt history (input field)

Last 10 submitted prompts stored in localStorage. Navigate with ↑ / ↓ arrow keys in the input field while it is empty. The current draft is preserved when you start browsing. Deduplicates consecutive identical entries. Index resets to −1 on submit.

Edit message

User messages: clicking Edit loads the text back into the input field (highlighted to show edit mode) and sets state.editingMessageIndex. Submitting replaces that message in history instead of appending a new one.

Assistant messages: opens the bubble for inline editing directly. The edited text is saved to state.messages and persisted to disk.

Session Author's Note override

In the Tools tab (right sidebar), the Author's Note field operates as a session-only override. It is stored in state.sessionAuthorNote and state.sessionAuthorNoteDepth — never written back to the character config file. Closing the chat discards it. To make changes permanent, edit the character config directly.

Avatar generation

Edit character config → Generate Avatar button. Takes the first 500 characters of character_card as the image description, prepends a strict photorealistic portrait prompt, calls Venice image generation with the safety checker disabled. Shows a preview — user keeps or regenerates. Stored as a base64 data URI in avatar_url.

Prompt Monitor

Right sidebar → Prompt Monitor tab. Calls POST /api/preview_prompt and shows the fully assembled payload that will be sent to the model on the next turn — all system messages, summary stack, RAG chunks, anchors injections, author's note at its injected position, full conversation history. Includes a token count and context usage gauge. Has a Summarize Now button for manual summarisation triggers.

Context gauge

A pie-chart indicator in the interface shows current token usage vs. the model's context window. Token counting uses tiktoken cl100k_base encoding with 4-token overhead per message. Falls back to length / 4 if tiktoken is unavailable.

Writing Tools — defaults and customisation

The four default tools (stored in messages.js:DEFAULT_WRITING_TOOLS):

LabelWhat the directive prompt instructs the model to do
Less Tell / More ShowRemove all emotion-labeling adjectives. Remove narrator explanations of what something "meant." Describe only physical actions, sounds, and sensations. Never explain — trust the reader to infer.
More Sensory DetailFocus on sensory detail (sight, sound, smell, touch) to make the scene more immersive.
Less Sensory DetailTrim redundant sensory stacking. Keep one strong detail per beat instead of three. Preserve emotional core and dialogue. Target ~70–80% of original length.
Add Inner MonologueAdd a short inner monologue in italics for the viewpoint character.

All labels and prompts are fully editable in Settings → Writing Tools. Customised tools are stored in localStorage:writing_tools_v2 as a JSON array of {id, label, prompt} objects. The defaults are used if the key is absent or the stored data is malformed.

Nudge vs Writing Tools: Writing Tools request a stylistic transformation of the existing output. Nudge injects a contextual author note that shapes how the model regenerates — more powerful for correcting character voice or narrative direction because it reads as author intent, not a rewrite command.

04 Dual Model Mode

Two AI characters conducting an automated conversation with each other. Model A responds to the user's opening prompt. Model B then receives Model A's response as a "user" message. They alternate until the turn limit is reached or you stop them.

Setup modal

FieldDetails
Character A / Character BDropdown of all saved character configs. Each brings its own system prompt, character card, temperature, and model.
Temperature slidersIndependent per character. Override the config's saved temperature for this session.
Model overrideOptional. Use a different model than what the character config specifies — useful for testing the same character with different models side by side.
Max turnsHow many alternations before the automation stops. Default: 10.
Initial promptThe opening user message that Model A responds to first.
Venice system prompt toggleinclude_venice_system_prompt — whether Venice's built-in system instruction is prepended. Default: true.

Execution

A 1500ms delay is enforced between turns (hardcoded). During each turn the active model streams its response normally via SSE. The streaming message appears with a model badge (character name) identifying who is speaking.

Message assembly per model: Model A receives the full conversation history with its own system prompt. Model B receives its own system prompt, and Model A's last response is presented as a user role message. Consecutive same-role messages are collapsed to avoid API rejections.

Control bar

ElementDetails
Character namesShows both character names with a divider — e.g. "Kelly ↔ Amy"
Turn counter"Turn 3 / 10" — updates after each completed exchange.
Status badgeRunning / Paused / Stopped / Inactive
Pause / ResumePause waits for the current turn to finish before halting. Resume continues from where it left off.
StopCancels the current stream via AbortController and ends automation.
ContinueOpens a modal to specify additional turns. Extends maxTurns and resumes.

Manual intervention

Clicking Regenerate or Delete on any message in a dual conversation pauses the automation automatically. This lets you correct a bad response without the system continuing on top of it. Resume from the control bar when you're satisfied.

State persistence

Dual model chats are saved with config.model === 'dual-model' as a marker. On load, the system auto-detects this, restores the control bar, turn count, and message attribution (model badges). Message actions available in dual mode: Copy, Fork, Regenerate, Delete pair. Edit, Keep, Read Aloud, and Writing Tools are not available.

05 Context & summary system

As a conversation grows, older messages have diminishing influence on generation. Lagoon's context system manages token load actively — counting, summarising, stacking, and injecting summaries so the model always has coherent historical awareness regardless of conversation length.

Token counting

Backend uses tiktoken cl100k_base encoding with 4-token overhead per message. Fallback: len(text) / 4. Context window sizes are configured per model in a CONTEXT_WINDOWS dict (default: 200,000 tokens). Auto-summarisation threshold: configurable (default 75%) — adjust via Memory Settings → Context Summarization.

Auto-summarisation trigger

On each chat request, manage_context() assembles the full LLM payload (config system messages + summary stack + recent conversation) and counts tokens. If the assembled payload exceeds the configured threshold (default 75%) of the context window and no summary is already pending review, a background summarisation job fires. It does not block the current request.

Pending review workflow

The generated summary is marked pending_review: true in the stack. A notification banner appears in the UI. No messages are pruned from disk until the user approves. On approval, the raw messages covered by the summary are deleted from the chat JSON, keeping only the configured number of recent message pairs (default: 5, adjust via Memory Settings → Messages to keep after prune). On rejection, the pending entry is deleted from the stack with no changes to history.

Summary stack structure

# chats/.summaries/{chat_id}.summary.json [ { "id": "uuid", "text": "narrative summary in flowing prose...", "message_count": 42, "model": "grok-4-20-beta", "created_at": "2026-03-25T14:30:00", "pending_review": true, // present only while awaiting approval "msgs_to_keep": 10 // how many recent messages to preserve on approval } ]

Summary injection format

Approved summaries are injected as system messages in the LLM payload. Single summary: wrapped as [PRIOR EVENTS]…[END PRIOR EVENTS — story continues…]. Multiple summaries: each gets a chain marker — [PRIOR EVENTS — Part 1 of N]…[END PART 1 — continued in Part 2].

Continuation-aware summarisation prompts

The summarisation prompt branches based on the stack state:

  • Empty stack (first summary): Full initial prompt — character state, setting, every event, dialogue beats, emotional shifts, sexual content if present, where the scene ended, loose threads. Target: thorough prose, past tense, third person, specific names not pronouns.
  • Approved summaries exist (continuation): The existing summaries are shown to the model explicitly. The directive is: do not repeat, rephrase, or summarise anything already recorded — cover only the new events from where the prior record ends. Prevents rehash and duplication between stack entries.

Summarisation model

Default: grok-4-20-beta. Max tokens: 10,000. Non-streaming synchronous call. Both are configurable via Memory Settings → Summarization model / Summary max tokens.

Force Summarize

Prompt Monitor → Summarize Now. Triggers POST /api/force_summarize which calls _generate_summary() directly with the same continuation-aware prompt. Adds the result to the stack as a pending review entry — same approval workflow as auto-generated summaries.

Context management APIs

06 Prompt assembly order

Every request assembles fresh. This is the order the model reads it — top to bottom, bottom has most influence on generation.

SYSTEM system_prompt permanent · from chat file
SYSTEM system_context + character_card permanent · from chat file
SYSTEM Summary stack — Part 1 of N … Part N of N (approved only) injected at request time
RAG Top-k semantically retrieved past chunks (defaults: top 3, ≥0.35 similarity, 800-token budget) — all configurable injected at request time
LORE Anchors entries triggered by keywords in last N messages (default: 15, priority-ordered, 4000-token budget) — all configurable injected at request time
NOTE Author's Note — inserted at depth N from the bottom of the conversation window injected at request time
OVERSEER Pending style correction notes (accepted violations from previous turn) prepended to next user turn only · ephemeral
ASST intro_statement (first message of conversation)
USER · · · recent conversation messages (pruned by context management) · · ·
USER ← current message — generation happens here
Key point: RAG chunks, anchors entries, and author's note are always injected fresh at request time. They are never part of the conversation history that gets summarised or pruned. They are always present regardless of how long the conversation has run.

07 Author's Note

What it is: A block of text re-injected at a fixed depth near the bottom of context on every single turn without exception. The model reads it right before generating.

What it's for: Things that are always true right now — character voice, accent, current tone, scene state, rules that drift when the model stops seeing them.

Two versions: persistent vs session

Persistent (stored in character config author_note): survives across sessions. Edit via character config editor or accept a Style Overseer violation (which appends a rule to it automatically).

Session override (state.sessionAuthorNote / state.sessionAuthorNoteDepth): edited in the Tools tab right sidebar. Discarded when the chat is closed. Never written back to the config file. Useful for in-session adjustments without permanently changing the character.

Depth

Depth = how many messages from the bottom of the conversation window the note is inserted before. The model reads the note, then reads the last N messages, then generates.

DepthEffectUse when
2Maximum influence. Right above the last 2 messages.Voice is still drifting; something critical must hold every turn
3Very strong. Recommended for character-critical voices.Specific accent, neurodivergent presentation, tight tonal rules
4Default. Solid, with room to breathe.Most characters
6+Lighter touch. Good for general scene anchoring.Loose vibe rather than strict voice enforcement

What to write

Not prose. Not a prompt. Director's notes. Bullet facts. Concrete and scannable beats better than elaborate paragraphs.

# Effective Author's Note — concrete, scannable, right before generation [Accent] North London, mild. Uses: mum, bloody, innit, proper, rubbish [Tone] sardonic, flat affect, dry. Emotions stated as facts not performed [Scene] Amy's flat, 7th floor, Scotland. Evening. Raining. [Voice] She reacts. She doesn't echo. Short responses unless hyperfixating.
The Style Overseer connection: Every time you accept a violation in the Style Overseer, it appends a DO NOT: {excerpt} — {suggestion} line to the persistent author's note and saves the config. The note compounds over time as a record of specific caught patterns for this character.

08 Anchors

What it is: Keyword-triggered entries that inject facts into context only when relevant. Nothing fires unless a keyword appears in recent messages — so you can store detailed world and character information without it consuming tokens every turn.

How to open it

Right sidebar → Tools tab → Anchors button. Only visible during character chats.

Entry structure

FieldDetails
KeywordsComma-separated. Any match in the last N messages triggers injection (default: 15, configurable via Memory Settings). Case-insensitive. Word-boundary matched — "mum" won't match "museum".
ContentThe text injected as a system message when the entry fires. Plain language, not a prompt.
PriorityInteger. Higher fires first. If multiple entries match and the total exceeds the token budget (default: 4000 tokens, configurable), lowest-priority entries are dropped.
Character not yet awareCheckbox. Changes injection format and enables automated reveal tracking. See section 11.

What to put in entries

Specific facts the model tends to get wrong or forget. Secondary character backstories, location details, relationship dynamics, medical/neurodivergent specifics, plot facts that keep getting misremembered. The more precise the content, the more useful the entry.

# Example entry — secondary character backstory keywords: mum, mother, mam priority: 8 content: Kelly's mother: London native, homophobic, abusive, controlling. Recently arrested for assault — claw marks on Kelly's arm. Kelly remains deeply attached despite everything. Autistic attachment pattern: cannot sever bonds even harmful ones. She still loves her mum. This is not weakness.

Good candidates for anchors entries

A secondary character's history, motivation, relationship to protagonist7–10

09 Character Awareness — automated reveal tracking

The problem: Anchors entries often describe facts the character doesn't know yet — a backstory, a secret, something revealed later. Previously this required manually editing the entry when a reveal happened in the story. In a long session that breaks flow.

The solution: The model signals its own reveals. When it writes a response in which the character learns something, it emits a hidden text token. The backend intercepts it, flips the entry to "known," and notifies you — without you touching anything.

How the injection changes

Normal entry (character_aware = true): injected as a plain fact.

Unaware entry (character_aware = false): injected as a two-part message — the fact (for author context) plus a contract with the model:

# What the model sees when character_aware = false [Lore | id:abc123 | Kelly not yet aware] Amy is originally from New Haven, CT. → If Kelly learns this during this response, include [LORE_UPDATE:abc123] anywhere in your output (it will be stripped before display).

What happens when the signal fires

  • [LORE_UPDATE:abc123] is stripped from the response text — you never see it
  • The entry flips to character_aware = true on disk immediately
  • A toast notification appears: "Now aware: amy, girlfriend"
  • Every subsequent turn, the entry injects as a normal known fact with no special framing
Zero false positives by design. The model only emits the signal when it's actively writing the reveal in that response. It reads the narrative it just produced and decides — it's not guessing from keywords. This works with any model; stronger models (Grok, Claude, GLM5) are more reliable than weaker ones.

How to enable it

Anchors editor → Edit any entry → check "Character not yet aware". The entry shows as muted/italic in the list with a "not yet aware" badge. Uncheck manually at any time if the model missed a reveal.

10 RAG Memory

After every response, a background process chunks the conversation and stores embeddings. Before every subsequent turn, your message is compared against all stored chunks and the most semantically relevant past exchanges are injected silently as context. You never touch this — it runs automatically.

Mechanics

StepDetailsDefault
Embedding modelall-MiniLM-L6-v2 · 384-dimensional vectors · runs locally—
Enabled toggleCan be fully disabled — stops both indexing and retrievalOn
Chunk sizeTurn-pairs per chunk. Changing this only affects newly embedded messages.4
TriggerAfter each completed assistant response, background embedding job runs—
RetrievalYour next message is embedded and compared via cosine similarity against all stored chunks—
ThresholdMinimum cosine similarity to include a chunk0.35
Top-kMax chunks retrieved per query3
Token budgetMax tokens of retrieved content injected per turn800
Injection positionBefore anchors entries — see prompt assembly diagram (section 08)—

All configurable parameters (enabled, chunk size, threshold, top-k, token budget) are adjustable via Settings → Memory Settings without restart.

When it starts helping

After roughly 8–10 turns — enough chunks need to be stored before retrieval becomes meaningful. In a 20,000-word session it becomes the mechanism that surfaces "she mentioned her brother on page 4" without you tracking it.

Semantic, not keyword: RAG retrieves by meaning similarity, not exact text. "The inspector examined the floor" may retrieve a chunk about the factory from 30 turns ago because both involve investigation. It's imprecise by nature — it doesn't need to be perfect to be useful.

11 Style Overseer

The problem: LLMs have strong training weight for bad fiction habits — isolated dramatic sentences, beat-only paragraphs, fragment continuations, POV slippage, correction acknowledgment. System prompt rules compete with all other context and fade as the window fills. One uncorrected violation normalises the pattern.

What it does: After every streamed response, a secondary LLM call reviews the output and flags violations inline on the message bubble. Each violation can be accepted (strengthens the Author's Note) or dismissed. Operates entirely post-stream — the main chat flow is never blocked.

How to enable

Character config → Toggles → Style Overseer checkbox. Per-character — only active for characters where you explicitly enable it. CoT content is stripped from the text before it is sent to the overseer — <think>…</think> blocks are removed so the model reviews only the visible prose.

The model

grok-4-20-beta via Venice. Temperature: 0.1. Max tokens: 2000. Single non-streaming call per response. No character card, no lore, no conversation history — just the response text and the rules prompt.

Rules

The rule set is fully configurable. Six built-ins run by default and can be toggled off. You write any additional rules you want in the Overseer tab (right sidebar) — one per line, plain English. Your custom rules append as RULE 7, 8, … and are stored in localStorage:overseer_custom_rules. Four model-specific presets load a curated starting set tuned for common quirks of that model.

Built-in baseline rules (always active)

  • R1 No isolated single sentences as their own paragraph — dramatic line isolation. Structural fix: paragraph rewrite.
  • R2 No double blank lines between paragraphs. Structural fix: paragraph rewrite.
  • R3 Strict 3rd-person limited POV. No narrating another character's inner state or intent. Lexical fix: string replacement.
  • R4 No correction acknowledgment. "I've adjusted," "you're right," "noted," "as instructed" — breaks the fiction frame. Lexical fix.
  • R5 No verbatim echo of the user's input phrasing. Lexical fix.
  • R6 No unattributed dialogue. Every line needs a clear speaker via tag or adjacent action. Lexical fix.

Rule scopes — how fixes are applied

Rules 1–2 are structural: the model returns a full paragraph rewrite. Rules 3+ are lexical: the model returns an exact replacement string that is swapped in-place. Custom rules are treated as lexical (3+) by default.

Model presets

PresetTargets
GLMSentence fragments as beats, trailing kickers, correction acknowledgment, verbatim echo, POV slippage
DeepSeekPurple prose, excessive em-dashes, correction acknowledgment, unattributed dialogue, POV

UI: badge and tooltip

After the stream ends, an amber spinner appears while the overseer call runs (grok is slow). If violations are found, a ⚑ N badge appears in the assistant message action bar. N is the violation count. Clicking it opens a tooltip showing all violations. The chat auto-scrolls to show the tooltip when it opens.

InteractionWhat happens

Corrected text is marked with an amber dotted underline; hovering shows the original phrase in a browser tooltip. 3. Auto-accept mode

Overseer tab → Auto-accept corrections checkbox (persisted in localStorage:overseer_auto_accept). When active, the overseer runs silently after each response: no badge, no tooltip. All violations are applied as in-place text replacements, each corrected passage is marked with an amber dotted underline, the author's note is updated for each violation, and the chat is saved. CoT content (<think>…</think>) is stripped before replacements are applied and is not included in the saved message.

The compounding mechanism: Each accepted violation appends a specific DO NOT line to the Author's Note, which is re-injected near generation point on every subsequent turn. As sessions progress, the author's note builds up a precise, character-specific record of caught patterns — and the constraints compound because they're always present at the highest-influence position in context.

Settings are written to memory_settings.json in the project root. The backend reads this file on each request (with a mtime-based cache) so changes are live immediately after saving — no server restart required. If the file does not exist, all defaults apply.

Why this matters: GLM 5 (and other models with smaller effective windows) write noticeably better output when the memory stack overhead is reduced. If you notice quality degradation on long chats — try lowering the lore token budget, reducing RAG top-k, or bumping the summarise threshold down so summaries fire earlier and keep the raw context window lighter.

13 Providers & Custom Endpoints

Lagoon supports four built-in cloud providers and an open-ended custom endpoint system for any OpenAI-compatible local inference server.

Built-in providers

ProviderNotes
Venice.aiPrimary provider. Full feature support including Venice E2EE (ECDH/HKDF/AES-GCM encrypted inference on 10 TEE models), web search, uncensored variants, balance display.
Together.aiLarge model catalog, fast inference. Most models in the default registry are Together-hosted.

Custom Endpoints

Any server that exposes an OpenAI-compatible /v1/chat/completions endpoint works. Gear menu → Custom Endpoints → Add Endpoint. Provide a display name, base URL, model ID, and optional API key. The endpoint appears in the model dropdown immediately — no restart required.

The model ID field is whatever you want sent in the "model" field of the API request. Most local servers ignore it or accept anything — check your tool's docs if you're unsure.

Model registry

Built-in models are defined statically in model_configs.json. The registry does not auto-discover models at runtime — this is intentional, keeping the list clean and predictable. Ollama and Custom Endpoints are the dynamic layers for adding models without touching config files.

14 Quick setup for a new character

1 — System Prompt + Character Card

Core identity. Permanent — never pruned. Who the character fundamentally is. Write it once, rarely touch it again.

2 — Author's Note

Always-true right now facts: voice, accent, tone, current scene state. Your highest-leverage tool. Set depth to 3 for tight character voices, 4 for everything else. If something is drifting, lower depth by 1 before anything else.

3 — Anchors

5–10 precise entries beats 30 vague ones. Add backstory facts the model gets wrong, location details, relationship dynamics. For facts the character doesn't know yet, check "Character not yet aware" — the system handles the reveal transition automatically.

4 — RAG

Let it run in the background — defaults are fine for most cases. It starts contributing meaningfully after about 10 turns. If a model feels slow or context-heavy, reduce top-k (try 1–2) or lower the similarity threshold slightly via Memory Settings.

5 — Style Overseer (optional)

Enable in Toggles if you want post-stream prose review. Start in badge mode — review each violation and accept the ones that matter to build up the Author's Note organically. Switch to auto-accept once you've established a clean baseline.

6 — Dual Model (optional)

When you want two characters to interact autonomously. Create a second character config first. Set a realistic turn limit (8–12 for meaningful exchanges without runaway repetition). Use the Continue button to extend if a scene is going well.
